# Build-time enhancer and regions

A view re-runs as a whole (ADR 0031), and a parent's patch carries the full HTML of every child it places, changed or not. That keeps the API plain, with no suppliers at call sites (ADR 0005), but costs CPU on every re-run and makes payloads grow with the page rather than with the change: one cell of a big table re-sends the table. Solid avoids this with a compiler that turns each JSX expression into its own render effect. Here the counterpart is the **enhancer**: a build step of the Maven and Gradle plugins that rewrites compiled classes. It changes cost, never behaviour. An app run from plain classes is fully functional and shows the same pages.

## Why bytecode, at build time

- Not an annotation processor: processors may not change existing code, and the ones that do (Lombok) make javac and ECJ disagree (ADR 0008). The processor keeps its jobs (checks, Retained State keys, client module types).
- Not a Java agent: it needs JVM flags in every launch configuration and server, and the bytes that run are not the bytes that were built.
- Rewriting class files after javac or ECJ, with ASM shaded into a `j2act-enhancer` library (relocated to `j2act.enhancer.asm`, its BSD license in `META-INF/LICENSE-asm.txt`, and no ASM in the published pom, since a Gradle build script's plugins share one classpath), run by the existing plugins (ADR 0025): an `enhance` goal bound to `process-classes` in `j2act-maven-plugin`, a task after `compileJava` in `j2act-gradle-plugin`. Output is deterministic (region methods numbered in source order, no timestamps), an already stamped class is skipped, only changed classes are rewritten (the Gradle task is cacheable), and extracted code keeps its line numbers so stack traces point at the user's line. Kotlin is out of scope.

## Only what gets packaged

The enhancer rewrites the jar, the war and the exploded deployments (`target/exploded`, `build/exploded`), not `target/classes` or `build/classes`. An IDE's hot code replace swaps in classes from javac or ECJ, which standard HotSwap refuses over an enhanced class of another shape and JetBrains Runtime accepts while silently dropping its regions. So dev mode and IDE runs stay plain, and they exercise the "same pages without the enhancer" rule every day.

In Maven the `enhance` goal, at `prepare-package`, keeps a copy of the classes in `target/j2act-classes`, copying what is newer, enhances it, and makes it the build's output directory for the goals after it: Maven reads `${project.build.outputDirectory}` for a goal's parameters only when the goal runs, so the jar and war plugins package the copy without being configured, and tests, a phase earlier, ran on the plain classes. Exploded deployments stay plain by default: they are dev mode's other way to run, made from whichever compiler last wrote the classes, the build's or the IDE's. `-Dj2act.enhance.skip` builds the plain app.

One opt-in, `classFolders`, enhances the build's own class folders in place, so everything run from them runs enhanced: tests, the app run from the build, an exploded WAR made from the build's classes. It is for profiling and for trying the enhanced app while developing. It is a setting the build keeps, `<classFolders>true</classFolders>` in the goal's configuration or `j2act { enhance { classFolders = true } }`, and a property for a single build, `-Dj2act.enhance.classFolders=true` or `-Pj2act.enhance.classFolders=true`; `skip` has both shapes too. What an IDE compiles into its own folders stays plain, and a plain class it compiles over an enhanced one needs enhanced redefinition to hot-swap. Gradle makes the flag an input of `compileJava`, so turning it off compiles plain classes again; Maven does not recompile unchanged sources, so its goal warns until `mvn clean`.

Enhanced classes call core internals (`Regions.of`, `StoreReads.field`), so the plugin fails the build when the core on the compile classpath is not its own version, and each enhanced class carries a `j2act$enhanced` stamp that the runtime checks at startup, refusing to start on a version it does not support. There is no tolerant call protocol between versions.

## Regions

A **region** is a part of a view that the enhancer cut out to run on its own: its own reads, its own patch, no state of its own (CONTEXT.md). Cut sites are arguments of static type `DomContent`, or elements of a `DomContent...` vararg, passed to a child-taking method (the generated tag factories and `with(...)`, `each(...)` row lambdas, component factory children, `loading(...)`, `errored(...)`), and the arguments of the generated attribute `with*` methods. A component's Props are not cut: the region around `userRow().withUser(x.get())` is small, and the child re-renders only if its Prop changed.

ASM's `Analyzer` with a `SourceInterpreter` finds the instructions that produced each argument. A self-contained range, with no jump into or out of it and no handler spanning its edge, moves into a synthetic method passed as a `Supplier` to `Regions.of(...)`. Anything else stays inline, and its view re-runs for it as today; the build reports how many sites stayed uncut. Fixtures run under javac and ECJ, as `ProcessorTest` does. A region whose first run read nothing folds back into its parent and gets no anchor, as Solid drops an effect without dependencies.

Granularity is per expression, text included, which matters most for editors and streamed chat messages, where one text node changes many times a second. A region sits between comment markers. The HTML parser keeps comments where it moves elements out (inside `tbody`, `tr`, `select`), and comments do not change `:empty` or `:first-child`. Where markers cannot go, the region moves up: inside `textarea`, `title`, `script` and `style` the element re-renders whole, and so does a `table` for what stands directly in it, since the parser puts a `tr` there into a `tbody` it makes, and a closing marker after it would land in another parent than the opening one (a view's own `tbody`, `thead` or `tfoot` keeps its rows granular, and `j2act-processor` warns at a `tr` given straight to `table(...)`, as Solid, Svelte and Vue reject or warn at markup the parser would change; no stub stands directly in a `table` either), and inside a `template`'s content, the view's own or a pending element's, what is cut out is part of the view around it, attribute regions included: that content is out of the document, where the client finds no markers, marks or stubs, and a controlled field's value still goes in only through `fields.ts` (ADR 0034). An attribute expression is an attribute region. The enhancer moves the arguments of a tag's `with*(...)` or `attr(...)` into a supplier and the call into a setter, and `Regions.attr(tag, supplier, setter)` makes that call now, as the plain build did, and again on its own whenever what the value read changes, so what the attribute becomes is what the app's own call makes of the value. Which attributes those are it learns from what each call writes on the tag, and each run starts from what they were before the call, so a `withCondClass(false, ...)` takes away what a true one set. A later call of the chain writing the same attribute wins in the plain build, and so does the view: such a region, or one whose run writes an attribute its first did not, has the view run again rather than patch. Its element carries `data-j2-a-sN=""` per attribute region, and a change sends `{type: "attrs", anchor, values}`, each attribute set or removed only after the same `beforeAttributeUpdated` a morph asks. Form fields (`input`, `textarea`, `select`, `option`) get none: their value, checked and selected are merged with what the user does (ADR 0013, 0034), so their attributes stay part of the view, as do `html`'s and `head`'s, which render with the document.

A cut's first value is what its supplier returned as its node was made, which is what the plain build's expression gave in whatever was running, a guess or a transition included. Not `peek`, which gives what is committed and nothing for a node made during a guess, and not a read, which a render counts as one and a hold with it.

**A region's owner is where it was created; its place on the page is only where it renders.** Not-ready and error reads travel the owner chain, so they stop at the boundary that would have caught the plain build's read. `loading(p(user.get()))` reads before the boundary exists in both builds, and the lambda form `loading(() -> ...)` means "inside the boundary" in both. ADR 0031 said the compile step could insert that lambda; it does not, because that would show a different fallback in an enhanced build, and the processor's warning for a direct read in a boundary's arguments stays.

Regions make Solid's rule ours: an expression in a view must be safe to run again on its own. A view that reads an iterator twice, `p(it.next())` beside `p(it.next() + count.get())`, works today and breaks enhanced. The docs say so, and `@WholeView` on a component or method leaves it uncut.

## One morph path

Dev and prod must not drift into two morph algorithms. Idiomorph's outerHTML morph is already a range morph, `morphChildren(ctx, parent, newContent, start, end)`, so the bundled Idiomorph is patched to expose that one function, and every patch goes through it with `morph.ts`'s callbacks: a whole scope in a plain build, a marker range in an enhanced one. An attribute patch asks the same `beforeAttributeUpdated` first, so focus, controlled values and pending state behave as in a full morph. If exposing it ever takes more than a narrow export, this decision is reopened. The demo is built plain and enhanced, and every browser check passes on both.

A patch, list operation or attribute patch that cannot find its anchor, because an extension, a translation tool or a client module moved or removed the markers, asks for the nearest component scope to be sent again whole through the repair path; dev mode warns.

## Lists

An `each(...)` row is a region keyed by its `withKey`, or by position without one (ADR 0019). The enhancer leaves the row's lambda or method reference as it is and points the call site of `each` (`TagHelpers`' or `TagCreator`'s) at a bridge returning `Regions.row(() -> row(item))`, a region that stays one even when it reads nothing, since rows of plain data are what a list most often holds; so what a row reads runs only that row, and a row whose content is a component, or a stream of them, is already a scope of its own. A child or row whose output equals what the page has is sent as a "same" stub that the client keeps; this part needs no enhancer and lands in core first, so plain builds stop re-sending unchanged children too. What the page has is counted from the served page, from what the response streams and from socket patches, and only for a scope the page has a place for, since a child's patch that runs ahead of its parent's during a hold is not applied. A scope's own patch updates what is recorded around it, its old HTML replaced by its new, so a row patching itself leaves its list's record whole. The stream's swap script finds a region by its markers and sets an attribute region's attributes, as runtime.js does. A child holding a controlled field is always sent whole, because `fields.ts` merges the user's typing with every answer (ADR 0034). A resync forgets it all, and a stub whose element the client cannot find asks for one. List operations then replace a list's stubs. A region whose content is only regions, its rows, and whose recorded content on the page was only its rows too, sends `{type: "list", anchor, ops}` instead of a patch: the server keeps the order of rows the page has and diffs it with the new one, rows that stay being a longest increasing subsequence of new places in old order, into remove (`r`), insert after a row or at the start (`i`, with its HTML), move after a row (`m`) and patch (`p`) for a row whose content changed or that holds a controlled field. The client applies them in order to marker ranges, moving with `moveBefore` where the browser has it, and keeping focus where it has not. A removed row's components go when the patch removing them goes (`Scope.pageHas`). Unlike a morph, an operation is not idempotent; ADR 0032 already applies each message once, since a reconnect resends only what follows the client's `seen`. Rows without a key are matched by position, so a filtered unkeyed list removes from the end and patches the rows whose content moved up; a key keeps a row with its item.

## Tracked classes

The enhancer makes tracked every class of the module's output that a store would hold as a bean: concrete, with a constructor taking nothing and private fields of its own, and not j2act's, the JDK's, a collection, a component, a store or a tag; `trackExcludes` (`<trackExcludes>` in Maven, `j2act { enhance { trackExcludes = [...] } }` in Gradle) leaves packages out. Private fields only, because a tracked object is handed out subscribing to nothing: a read the enhancer did not rewrite would subscribe to nothing, and a private field is read only in its class and its nestmates, which are compiled together. For the same reason no superclass may have fields: a superclass is never tracked itself, so its reads stay plain. And the other way round: the runtime counts a class as tracked only when it implements `Tracked` itself, so a subclass, whose own fields' reads the enhancer did not rewrite, is read whole. Records stay as they are: a store reads them whole. Which classes enter a store cannot be told at build time; a class that never does pays one field and a cheap call per read. Each read of a tracked field, in any class of the app, becomes `StoreReads.value(object, own, "name", type)`. It compares what the store holds now with the object's own value by identity, a string, number, boolean, character or enum by value: a store hands out one snapshot until something in it changes, and an entity equal by its id is still a new one.

A handed-out object stays the version it was, as ADR 0035 has it, in both builds. Regions make that meet a case the plain build never has: a region keeps an object its view fetched, and when the store moves on, only the region runs again, on the old copy. So `value` also compares the object's own value with what the store has now; when they differ while a cut's supplier runs, the cut's creator is marked to render again within the same job, which fetches the current version and makes the cut anew, as the plain build's view, subscribed to the whole object, would have run again. Tracking then saves the runs where an object is read where it is fetched, and for fields nobody reads. Live reads, Solid's proxy behaviour, were rejected: an app that keeps a handed-out object, to undo or to compare, would read other values enhanced than plain.

## How it is checked

Every `RandomAppTest` and `ConsistencyTest` seed runs twice, over plain and enhanced classes, and wants the same page after every step, no more view runs and no larger patches in the enhanced run. This is the release gate.

## Milestones

1. "Same" stubs in core, no enhancer.
2. The enhancer with regions and attribute regions, markers, the range morph and repair.
3. `each(...)` rows as regions.
4. Keyed list operations, with keyed inserts, moves and removals of stateful rows in `RandomAppTest`.
5. Tracked classes (ADR 0035), built.
6. Static hoisting, built: a child expression made only of literals, tag factories and withers over them, text and strings joined from literals (no local, field, jump, lambda or other call) is built once into a static field of its class, through `Regions.hoist`, and its first render keeps its HTML for every later one, by every tab. It sends what the plain build sends; it saves the building and the rendering. Inside raw text it renders as its tree. The arguments of `html(...)` are neither cut nor hoisted, since a page's head and body are found by what they are. A constant kept in a static field outlives a hot swap of its class, which only `classFolders` would meet.

1 to 4 are the first release; 4 may slip without holding up 1 to 3.

## Rejected

- Element-only regions, anchored on the element an expression produces, with text and fragments moving up to their parent. No new morph primitive, but a streamed text re-sends its element tree, and wrapper elements cannot sit in tables where comments can.
- Not cutting inside boundary or component-children arguments, to keep which boundary catches a read. It gives up `card(table(rows...))`; owning a region where it was created keeps the same answer.
- Prop regions, Solid's getter props. The region around the component description already re-runs alone.
- Choosing tracked classes by annotation, or from what the processor sees passed to `createStore`; the latter misses nested types and generics.
