# Explicit unsafe and socket trust

Text escapes by default with no silent off-switch: raw HTML goes through one loud unsafeHtml() entry point (React dangerouslySetInnerHTML analogue), flagged by a build-time processor that runs under javac in Gradle/Maven and under JDTLS, so IDE and CI warn identically. Same loud treatment for javascript:/data: URLs in href/src, guard-bypass markers on routes, and unbounded in-memory upload buffering. Route-structure diagnostics ride the same processor pipeline under javac (Gradle/Maven) and JDTLS: a non-Layout class in layout() position is a hard error in both, mirroring Next.js build errors. A query loader that captures a render() local without withKey is a warning from the same processor (ADR 0020). Uncertain dynamic cases are reported at runtime in the browser console and the server log, never silently.

Verification spike before the processor is relied on: one processor jar, one fixture project, run under javac (Maven), JDTLS/ECJ (VS Code) and Eclipse. The fixture covers every check that reads method bodies: unsafeHtml() in a render, a javascript: href literal, a non-Layout class in layout(), and a component factory inside each() and Stream.map() lambdas without withKey (ADR 0019). Pass means the same diagnostics (message, severity, source position) in all three. Experience so far says javac and ECJ agree unless bytecode-rewriting processors like Lombok are involved; the spike confirms it for these checks and records any gap as a runtime report in the browser console and the server log.

Spike outcome: it passes, and j2act-processor is that jar. The standard processor API has no method bodies, so each compiler gets a small adapter: javac through its public Trees API (unwrapping the environments Gradle and IntelliJ wrap around it), ECJ through two internal seams reached by reflection, so the jar never links against ECJ. First, ECJ parses bodies only after processors run, so the adapter asks the compiler's own parser for them early, which is what ECJ does anyway before resolving. Second, Messager points only at elements, so the adapter moves the element's declaration positions to the node for the duration of the call. Both adapters convert to one neutral syntax tree, and the checks run once on it. Neither compiler has attributed types at that stage, so the checks resolve names themselves from imports and javax.lang.model and ignore what they cannot resolve. ProcessorTest compiles the fixtures with javac and with ECJ and requires identical diagnostics, including offsets. tools/jdtls-check.mjs gets the same result from the VS Code language server through m2e-apt. Desktop Eclipse runs the same JDT compiler and APT code as JDTLS but has not been run separately.

Three planned checks turned out to need no processor code. The type system already rejects a non-Layout class in layout(): the parameter is Class<? extends Layout>, and both compilers fail on it (the fixture pins this). No guard-bypass marker exists in the route API, and uploads stream to disk under withMaxFileSize, so nothing buffers without a bound. Those two checks arrive with the first API that needs them.

The opt-out is @AllowUnsafe("why it is safe") on the method, field or type, not @SuppressWarnings("j2act"). ECJ warns about @SuppressWarnings tokens it does not know (unhandledWarningToken, on by default), so every suppression would itself trade one warning for another in VS Code and Eclipse. A reason string also keeps the escape hatch loud in review, like Rust's unsafe blocks with a SAFETY comment. It covers only raw HTML and script URLs. A missing key or a captured local is fixed by writing withKey, which is the point of those warnings.

Sockets accept event invocations, so first paint mints a per-session CSRF token and every WS event and upload chunk is validated against it plus Origin/Host checks. Auth re-checks mean nothing if a foreign site can drive the victim's session.
