# Component identity: held objects, tree slots, item-keyed each()

Every framework ties state to an instance. They differ in how a re-running render finds last render's instance: Solid and Vaadin never re-run, React, Vue and Compose match by tree position (Compose via a compiler plugin we rule out, ADR 0002), and LiveView demands explicit ids. We use Java object identity where the user has it and tree position where they don't, with no key attribute.

A held object is its own identity. A component instance stored in a field or variable and rendered again (c rather than c()) is recognised by reference: same object, same State, and its with* props stay as last set, because the user holds that object. Rendering one object in two places at once is a dev-mode error, like appending one DOM node twice.

A factory call is a fresh description. c() builds a new object every render, so its props start from defaults and plain fields reset, the React element model. Its reactive primitives (state, computed, query, mutation, effect), whether field initializers or locals in render(), are unbound until the framework places the object in the tree, then bind to the slot at that position: parent scope, child index with null children holding their index (so cond ? a() : null never shifts later siblings), and component class. The same slot and creation order return the same State. Creating primitives conditionally breaks creation order, and dev mode fails fast when a slot's sequence of primitive types changes between renders. Primitives stay allowed inside render() because computeds and queries close over props that only exist per render.

Lists key by item, not by attribute. each(items, fn) knows which item produced each child and binds that child's slot by the item's equals()/hashCode(), as Solid's For keys by item reference. Records, value objects and entities with id-based equals keep their row State across reorder, filter and refetch with nothing extra. Data without meaningful equals (entities re-fetched as new objects with identity equals) needs an extractor on the each() call, e.g. each(users, User::getId, u -> userRow().withUser(u)). That is the only key in the API, and it lives on the list, never on an element. Duplicate keys fall back to position with a dev warning.

Idiomorph is not a substitute for this. It matches DOM nodes on the client after the server has already decided which State rendered which row, so it keeps focus and DOM-local state but cannot move server State to the right row. Stateless rows need no identity at all, and position plus Idiomorph is enough for them.
