# Component identity: held objects, tree slots, row keys

Every framework ties state to an instance. They differ in how a re-running render finds last render's instance: Solid and Vaadin never re-run, React, Vue and Compose match by tree position (Compose via a compiler plugin we rule out, ADR 0002), and LiveView demands explicit ids. We use Java object identity where the user has it, tree position where they don't, and an explicit row key where position is not enough.

A held object is its own identity. A component instance stored in a field or variable and rendered again (c rather than c()) is recognised by reference: same object, same State, and its with* props stay as last set, because the user holds that object. Rendering one object in two places at once is a dev-mode error, like appending one DOM node twice.

A factory call is a fresh description. c() builds a new object every render, so its props start from defaults and plain fields reset, the React element model. Its reactive primitives (state, computed, query, mutation, effect), whether field initializers or locals in render(), are unbound until the framework places the object in the tree, then bind to the slot at that position: parent scope, child index with null children holding their index (so cond ? a() : null never shifts later siblings), and component class. The same slot and creation order return the same State. Creating primitives conditionally breaks creation order, and dev mode fails fast when a slot's sequence of primitive types changes between renders. Primitives stay allowed inside render() because computeds and queries close over props that only exist per render.

Lists key on the row, not on the list call. A repeated component takes withKey(...) as one more with* builder: each(users, u -> userRow().withUser(u).withKey(u.getId())). The key is any value with equals()/hashCode(), unique among siblings, used only to bind the slot and derive the morph anchor, never rendered as HTML. Because the key rides on the element, the same rule covers each(), users.stream().map(...).collect(...), and hand-built lists, and each() needs no overload whose lambda shapes the language server cannot tell apart. Without withKey, siblings bind by position. That is correct for stateless rows and wrong for stateful rows that reorder or filter.

Missing keys are caught in two layers. The build-time processor (ADR 0008, covered by its javac/ECJ spike) warns when a component factory call inside an each() or Stream.map() lambda has no withKey in its builder chain. The runtime is the precise backstop: in dev mode it warns when same-class stateful siblings without keys change count or order between renders, which is exactly the case where State would land on the wrong row. Duplicate keys among siblings fall back to position with a dev warning.

Idiomorph is not a substitute for this. It matches DOM nodes on the client after the server has already decided which State rendered which row, so it keeps focus and DOM-local state but cannot move server State to the right row. withKey is what tells the server. Stateless rows need no identity at all, and position plus Idiomorph is enough for them.
